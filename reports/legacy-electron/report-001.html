Summary

Implemented a comprehensive multi-device architecture refactoring across 6 phases using 6 parallel subagents. The nkEditor3 application was modularized from a single-device (nanoKONTROL2) MIDI CC remapper to a multi-device platform supporting arbitrary MIDI controllers. The Akai MidiMix was added as the first additional supported device.

Key changes include: a device abstraction layer with type-safe definitions, backend MIDI generalization for CC and Note message types, multi-device store architecture with per-device state isolation, device-specific UI editors, and a device-aware config/preset system. The test suite was expanded from 0 to 276 passing tests across 6 test suites, covering device definitions, stores, UI components, config parsing, preset creation, and backward compatibility regression.

Findings

Medium Device Abstraction — MidiMix Note vs CC Message Types
src/shared/devices/

The Akai MidiMix uses Note On/Off messages for its buttons while the nanoKONTROL2 uses CC messages for all controls. This fundamental protocol difference required introducing a messageType discriminator ('cc' | 'note') throughout the entire stack: device definitions, mapping entries, config parser, LED controller, and MIDI handler. The DeviceDefinition interface captures this at the control level via ControlDef.messageType, and the MappingEntry type gained an optional messageType field that defaults to 'cc' for backward compatibility.

Medium Backend MIDI — easymidi TypeScript Channel Narrowing
src/main/services/

The easymidi library's TypeScript typings require a Channel type (0-15 literal union) rather than a plain number for Note message sends. This required explicit type narrowing when constructing Note On/Off messages for MidiMix LED feedback and button output. The MIDI handler was generalized to dispatch to either send('cc', ...) or send('noteon', ...) / send('noteoff', ...) based on the mapping entry's messageType.

Low Store Architecture — Backward-Compatible Legacy APIs
src/renderer/stores/

Backward compatibility was maintained by keeping the legacy single-device Zustand store APIs alongside the new per-device APIs. The controls store retains the original tracks[] and transport state shape for existing nK2-specific components while adding a deviceControls: Map<string, ...> for multi-device state. This dual-API approach allows incremental migration without breaking existing UI code.

Low Config Parser — ESM/CJS Incompatibility in Test Environment
src/config-parser.ts, vite.config.ts

The vite-plugin-electron-renderer generates ESM shims for Node.js built-in modules (e.g., node_modules/.vite-electron-renderer/fs.mjs) that use require() internally. In the Vitest test environment, these shims fail with ReferenceError: require is not defined in ES module scope. Fixed by adding a test.alias configuration in vite.config.ts that maps all builtinModules to their native Node.js implementations, bypassing the vite-electron-renderer shims during test execution.

// vite.config.ts - test section
test: {
  alias: Object.fromEntries(
    builtinModules.flatMap((mod) => [
      [mod, mod],
      [`node:${mod}`, `node:${mod}`],
    ]),
  ),
}
Medium UI Components — MidiMix Requires Distinct Editor
src/renderer/components/

The MidiMix's 3-knob-per-track layout (vs nK2's 1 knob + 1 slider) required a distinct editor component (MidiMixEditor) rather than parameterizing the existing nK2 editor. The control layout differences are too significant for a single configurable component to handle cleanly: different knob counts, fader vs slider naming, button note numbers, and the absence of a transport section. A DeviceEditorContainer component routes to the appropriate editor based on the active device's ID.

Implementation Plan Updates

The refactoring was organized into 6 sequential phases, each handled by a dedicated subagent. All phases were designed with clear interfaces so that work could proceed in parallel where dependencies allowed.

  • Phase 1: Device Abstraction Layer — Created the DeviceDefinition interface, type system for controls (continuous/button), track layouts, LED protocol, and port patterns. Implemented definitions for nanoKONTROL2 and Akai MidiMix. Built a central registry with lookup-by-ID, auto-detection from port names, and enumeration.
  • Phase 2: Backend MIDI Generalization — Generalized the MIDI handler and mapping engine to support both CC and Note message types. Added composite lookup keys (messageType:channel:number) for input routing. Made the LED controller device-aware, sending CC or Note messages based on the device's LED protocol.
  • Phase 3: Multi-Device Store Architecture — Refactored Zustand stores for per-device state. Added a devices store for managing active/connected devices, per-device control state in the controls store, per-device undo stacks, and device-aware preset filtering. Maintained backward-compatible legacy APIs.
  • Phase 4: UI Components — Added DeviceSelector dropdown, DeviceTabBar for switching between active devices, DeviceEditorContainer for routing to device-specific editors, and MidiMixEditor with the 3-knob-per-track layout. Integrated AddDeviceDialog for adding new devices.
  • Phase 5: Config/Preset System — Extended the config parser with [device <id>] headers and note:N syntax. Added device-aware validation using device definitions. Created createDefaultMappingForDevice() factory and DeviceMappingConfig type. Added 3 MidiMix factory presets.
  • Phase 6: Integration, Testing, Documentation & Report — Fixed the ESM/CJS compatibility issue in the test environment. Added config-preset and regression test suites. Updated README with multi-device documentation. Generated this report.

Recommendations

  1. Hardware Testing — Test with a physical Akai MidiMix to verify LED feedback (Note-based) and button response. The current implementation is based on the MidiMix MIDI specification but has not been validated against the actual hardware in all edge cases (e.g., LED update timing, bank switching behavior).
  2. Config Parser ESM Fix Verification — The builtinModules alias approach in vite.config.ts resolves the test environment issue cleanly. Monitor for any side effects if vite-plugin-electron-renderer is updated, as the shim generation may change in future versions.
  3. Additional Devices — The architecture now supports easy addition of new devices. Recommended candidates: Novation Launch Control, Behringer X-Touch Mini, Arturia MiniLab. Each requires only a device definition file, registry entry, and (optionally) a custom editor component.
  4. DeviceMappingConfig Presets — Extend the preset system to use DeviceMappingConfig for full MidiMix control coverage. Currently, MidiMix presets use the nK2-shaped MappingConfig which can only represent 1 of the 3 knob rows. A DeviceMappingConfig-based preset would store all 3 knob rows, the master section, and device-specific metadata.
  5. Performance Monitoring — Monitor memory usage with multiple devices connected simultaneously. Each device adds a Zustand store slice and MIDI I/O channels. With 2 devices this is negligible, but scaling to 5+ concurrent devices may warrant pooling or lazy initialization of device state.
